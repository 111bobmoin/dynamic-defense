# 封装流量说明

这份说明用于指导另一个 AI 理解当前目录中的 pcap：中间链路里的后续流量并不是“原生可直接解析的 UDP/ICMP/TCP”，而是被封装在一个自定义 IPv4 载荷里；需要先拆封装，才能还原出真正的内层协议。

## 1. 先给结论

- `20260514_095254_s1_port1_ens8_host1-s1.pcap`
- `20260514_095254_s7_port2_ens8_s7-server1.pcap`

这两个文件是边界链路抓包，看到的是原始业务流量，当前样本里直接可见的是 `ICMP` 和 `UDP`。

- `20260514_095254_s1_port2_ens9_s1-s3.pcap`
- `20260514_095254_s3_port1_ens8_s1-s3.pcap`
- `20260514_095254_s3_port2_ens11_s3-s4.pcap`
- `20260514_095254_s4_port1_ens7_s3-s4.pcap`
- `20260514_095254_s4_port2_ens10_s4-s7.pcap`
- `20260514_095254_s7_port1_ens10_s4-s7.pcap`

这 6 个文件是中间转发链路抓包，包的外层 `IPv4 Protocol` 都是 `253`，说明它们承载的是“自定义封装报文”，不是原始 UDP/ICMP/TCP。

当前样本的实际统计结果如下：

- 边界入口 `host1-s1`：外层原生 `ICMP 15` 个，`UDP 9` 个。
- 边界出口 `s7-server1`：外层原生 `ICMP 17` 个，`UDP 9` 个。
- 中间链路各 pcap：外层全部是 `IPv4 proto 253`。
- 拆封后，当前样本实际观测到的内层协议只有 `ICMP(1)` 和 `UDP(17)`。
- `TCP(6)` 是这套封装规则理论上支持的内层协议类型之一，但这批样本里没有实际观测到 TCP 内层包。

因此，给另一个 AI 的正确表述应该是：

1. 中间链路里的后几条流量是“经过封装的内层流量”。
2. 内层协议号可以是 `UDP/ICMP/TCP` 等标准 IP 协议号。
3. 但就这批样本本身而言，已经验证到的是封装后的 `UDP` 和 `ICMP`，没有抓到封装后的 `TCP`。

## 2. 如何识别这是封装流量

识别规则很直接：

1. 先看以太网类型，必须是 `0x0800`，也就是外层是 IPv4。
2. 再看外层 IPv4 头的 `Protocol` 字段。
3. 如果该字段是 `253`，就说明这是自定义封装流量。
4. 外层 IPv4 头后面的负载，不是可以直接当 UDP/ICMP/TCP 解析的数据，而是：
   - 前 `29` 字节：自定义封装头
   - 之后的内容：真正的内层协议报文

目录中的 `proto253_decap.py` 已经验证了这件事，核心常量如下：

- `PROTO253 = 253`
- `INNER_PROTO_OFFSET = 4`
- `ENCAP_HEADER_LEN = 29`

这表示：

- 外层 IPv4 的 `Protocol = 253`
- 自定义封装头总长度是 `29` 字节
- 封装头内偏移 `4` 的那个字节，保存真实的“内层 IP 协议号”

协议号对应关系沿用标准 IP 协议号：

- `1 = ICMP`
- `6 = TCP`
- `17 = UDP`

## 3. 字节级拆封装规则

对任意一个外层 `IPv4 proto 253` 的报文，拆封装步骤如下：

1. 取以太网头后面的 IPv4 头。
2. 根据 IPv4 `IHL` 计算外层 IP 头长度，通常是 `20` 字节，但不要写死。
3. 取出外层 IP 负载 `payload = ip_packet[ihl:total_length]`。
4. 判断 `payload` 长度是否至少为 `29` 字节；不足则说明封装头不完整，不能正常拆。
5. 读取 `payload[4]`，这 1 个字节就是内层协议号：
   - `1` 表示内层是 ICMP
   - `6` 表示内层是 TCP
   - `17` 表示内层是 UDP
6. 去掉前 `29` 字节封装头，保留剩余部分：
   - `inner_payload = payload[29:]`
7. 用“原外层 IPv4 头”构造一个新的 IPv4 报文：
   - 保留原 IPv4 头的大部分字段
   - 把 `Protocol` 从 `253` 改成 `payload[4]`
   - 把 `Total Length` 改成 `ihl + len(inner_payload)`
   - 清空并重算 IPv4 Header Checksum
8. 新的二层帧应为：
   - 原以太网头
   - 新的 IPv4 头
   - `inner_payload`

这一步做完后，Wireshark/tcpdump/其他 AI 就能把该包按 `UDP`、`ICMP` 或 `TCP` 正常解析。

## 4. 为什么说“后几条”是封装流量

如果另一个 AI 重点在分析中间链路 pcap 中靠后的那些包，可以直接这样理解：

- 在 `s1-s3`、`s3-s4`、`s4-s7` 这些链路文件里，后面的包并不是“新的独立外层 253 协议业务”，而是前面原始业务流量在隧道中的继续转发结果。
- 这些包的外层协议统一显示为 `253`，只是运输壳。
- 真正要分析的业务类型在封装头后的内层数据里。

例如，在 `20260514_095254_s1_port2_ens9_s1-s3.pcap` 的第 1 个封装包中：

- 外层 IPv4 `Protocol = 253`
- 外层 IP 负载长度是 `80`
- 前 `29` 字节是封装头
- 封装头十六进制为：

```text
01291363110129170f00000000000000010129170f0129171000000000
```

- `payload[4] = 17`
- 说明内层协议是 `UDP`
- 去掉前 29 字节后，后面的负载开头为：

```text
3039d4310033396648656c6c6f206672
```

这里前 8 字节已经符合 UDP 头结构：

- 源端口 `0x3039 = 12345`
- 目的端口 `0xd431 = 54321`

这说明它不是“外层 253 上直接跑了一种新应用”，而是“UDP 被套进了 253 封装里”。

## 5. 直接可用的拆封装脚本

目录里已经有现成脚本：

- [proto253_decap.py](C:\Users\Administrator\Desktop\20260514_095254\proto253_decap.py)

它做的事就是：

1. 找到外层 `IPv4 proto 253` 报文
2. 去掉前 `29` 字节封装头
3. 将新的 IPv4 `Protocol` 改为内层协议号
4. 修正 `Total Length`
5. 重算 IPv4 Header Checksum
6. 输出新的 pcap 到 `decapped/`

批量拆封装命令：

```powershell
python .\proto253_decap.py *.pcap
```

单文件拆封装命令：

```powershell
python .\proto253_decap.py .\20260514_095254_s1_port2_ens9_s1-s3.pcap
```

输出文件默认在：

- `decapped\*_decap.pcap`

例如：

- `decapped\20260514_095254_s1_port2_ens9_s1-s3_decap.pcap`

拆完之后再用 Wireshark 或其他分析程序打开 `*_decap.pcap`，就会看到原本的内层 `UDP/ICMP`，如果未来样本里有 `TCP`，也会直接显示成 `TCP`。

## 6. 给另一个 AI 的建议说法

如果你要把这个事实传给另一个 AI，可以直接用下面这段描述：

```text
这些 pcap 里，边界链路 host1-s1 和 s7-server1 看到的是原始流量；中间链路 s1-s3、s3-s4、s4-s7 里的后续报文外层 IPv4 protocol 都是 253，说明它们是经过自定义封装后的隧道流量。拆封装方法是：读取外层 IPv4 负载，取第 5 个字节 payload[4] 作为内层协议号，去掉前 29 字节封装头，把剩余内容作为内层报文负载，再把外层 IPv4 头的 protocol 字段改为该内层协议号并重算 IP 校验和。协议号 1/6/17 分别对应 ICMP/TCP/UDP。当前这批样本实际观测到的内层协议是 ICMP 和 UDP，没有观测到 TCP，但拆封规则同样适用于 TCP。
```

## 7. 最重要的注意点

- 不要把 `proto 253` 直接当成某种业务协议去分析。
- `253` 只是外层承载标记，真正的业务协议要看 `payload[4]`。
- 不要假设外层 IP 头一定是固定 `20` 字节，应该根据 `IHL` 计算。
- 不要忘记去掉的是 `29` 字节封装头，不是 `20`、`24` 或别的长度。
- 重写 pcap 时，必须同步修正 IPv4 `Total Length` 和 `Header Checksum`。
- 当前样本已验证的是“封装 UDP/ICMP”；如果以后遇到 `payload[4] = 6`，应按同样方法还原为 TCP。
